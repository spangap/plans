# i18n — hash-keyed string translation for firmware and web (plan)

Status: design / not yet implemented.

## Goal

Internationalization (i18n) for **user-facing UI text only**: LVGL screen
text on the device and the browser UI's text. Explicitly out of scope:
log messages, CLI help, CLI command output, storage keys — those stay
English. Translations live in per-straddle files; missing or stale
translations fall back to English, never break anything.

It is gettext without the catalog machinery: strings are keyed by a hash
of the English text, tables are generated and sorted at build time, and
the runtime is one binary search.

## Runtime

Every user-facing string passes through one function:

```c
const char *i18n(const char *english);
```

- Language is English → return the argument unchanged (a branch, zero
  cost — English builds pay nothing).
- Otherwise: hash the string (32-bit Fowler–Noll–Vo hash, variant
  FNV-1a, over its UTF-8 bytes — per byte one XOR and one multiply, no
  tables, identical few-liner in C and JS),
  binary-search the current language's sorted table in rodata, return
  the translated string on a hit, the English argument on a miss.

Per language, the generated table is a sorted array of
`{uint32_t hash, uint32_t offset}` entries followed by a string pool of
NUL-terminated translations. The active language's table base pointer
is resolved once at boot — a language change forces a reboot (see
below), so nothing re-translates live; the English path never touches a
table. Offsets rather than
pointers keep entries relocation-free and could shrink to `uint16_t`
while a pool stays under 64 KiB, but pointers would also work — the
tables are link-time constants in a statically linked image.

### Rules at call sites

- `i18n()` takes **string literals only**. A string built at runtime is
  invisible to the build-time extractor: it cannot be translated and
  could silently hash-collide with a real key. The generator errors on
  call sites whose argument it cannot resolve to a literal.
- Translate the **format string, then format**:
  `snprintf(buf, sizeof buf, i18n("%d peers"), n)` — never the other
  way around, and never assemble sentences from concatenated fragments;
  fragments don't translate.
- Word order differs across languages, so multi-argument format strings
  need positional specifiers (`%1$s`). Verify the target libc's printf
  supports them before relying on multi-argument translations; until
  then, keep translated format strings to one argument.

## Translation files

One file per language per straddle, in the straddle root (e.g.
`nomad/de.i18n`). Each entry maps one English string — byte-for-byte the
literal in the source — to one translated string. Exact format TBD, but
it must round-trip escapes exactly as C literals do, since the hash is
over the bytes the compiler produces.

An English string that changes in source simply stops matching its old
translation and shows English until the file is updated — graceful
staleness, no build coupling.

## Build

```
sources ──extract i18n("…") literals──► key universe
key universe ──hash, check collisions──► error on any 4-byte collision
translation files + key universe ──► per-language sorted C tables (rodata)
                                 └─► per-language hash→text JSON for the web
```

A build step scans all staged straddle sources for `i18n(` call sites,
joining adjacent literals (`i18n("a " "b")`) and expanding through any
sanctioned wrapper macros. Because the extractor sees the **entire** key
universe — not just translated strings — every possible 4-byte collision
is visible at build time and fails the build; that is what makes the
truncated hash safe. Entries are emitted only for strings that have a
translation; everything else resolves to English via lookup miss, so a
partially translated language costs proportionally less flash.

The same generator emits both artifacts from the same translation files:
the C tables for firmware and, per language, a hash→text file served
gzipped from `/fixed` for the browser. Duplication is in bytes only,
never in maintenance.

## Web side

The browser gets the same `i18n(s)` function in JS, backed by the
fetched hash→text file for the active language, covering **only the
browser tree's own literals** (Vue panels, settings modules). The JS
hash must equal the C hash **byte-for-byte**: FNV-1a over the UTF-8
encoding of the string, not over UTF-16 code units. The web extractor
scans only `browser/` sources; it never harvests firmware C.

## Device-published display text

Some settings-row text is composed on the device and published through
storage (e.g. `wg.key_state` = "not set" / "generated"). That text is
translated **device-side**: the literal passes through `i18n()` at the
`storageSet` call site, so the wire carries the already-translated
string and the browser displays it verbatim. These call sites are
ordinary firmware `i18n()` literals — the firmware extractor already
sees them.

Two rules follow:

- **Never key on published display text.** It varies by language, so
  any comparison against it is broken by construction. Consumers render
  it; logic wants its own non-display key.
- A language change **forces a reboot**, like UI zoom. Publishers run
  at init, so everything re-publishes in the new language; no live
  re-translation machinery anywhere — not for published strings, not
  for LCD widgets.

## Cost (measured against current sources)

The current translatable surface — LVGL-facing literals across all
straddles in the tdeck build — is about 30 unique strings, under 0.5 KiB
of English. A full-coverage language is therefore roughly 1 KiB of flash
(8 B/entry index + translated pool at ~1.2× English); even ten times
today's UI text stays around 10 KiB per language. The lookup code will
outweigh any single table. Browser-side, the human-facing text across
all `browser/` trees and web interfaces measures roughly 250–350 unique
strings, 5–7 KiB of English — a per-language web file of ~2–3 KiB
gzipped in `/fixed`, costing no firmware flash.

For calibration, the deliberately excluded sets are the expensive ones:
CLI output is ~33 KiB of unique English and user-visible log lines
another ~54 KiB — keeping them out of scope is what keeps a language
near-free.

## Open points

- Translation file format (must preserve C-literal escape semantics).
- Where the language setting lives (a storage key) and how the browser
  learns/overrides it.
- Positional-specifier support in the target libc's printf.
- Whether wrapper macros around `i18n()` are allowed, and if so, the
  extractor's list of them.
